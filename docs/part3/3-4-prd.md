# 10. PRD — AI에게 줄 지시서 작성법

> 본 수업에서는 에이전트 정의를 짧게 작성했지만, 본업에서 본격 적용 시 좀 더 체계적인 **지시서**가 필요할 때가 있어요. 이걸 PRD(Product Requirements Document)라고 해요.

---

## [개념] PRD가 뭐예요?

**PRD = AI에게 "이런 결과물을 만들어줘" 라고 상세하게 적은 지시서.**

쉬운 비유:

> 신입 직원에게 일을 처음 시킬 때
> - 한 줄로 "이거 해줘" 라고 하면 → 결과물이 들쭉날쭉
> - 상세 지시서를 한 장 정리해서 주면 → 일관된 결과
>
> AI도 똑같아요. 자세한 지시서가 있으면 결과 품질이 안정돼요.

본 수업에서 만든 `.claude/agents/PM.md`, `.claude/agents/Editor.md` 가 작은 형태의 PRD라고 볼 수 있어요. 본업에 본격 적용할 땐 좀 더 풍부하게 작성하는 게 좋아요.

## [개념] PRD의 8가지 핵심 섹션

복잡한 작업일수록 아래 8가지를 포함하면 결과가 안정돼요.

### 1. 목적 (Why)
"이 결과물이 왜 필요한가?"

> 예: "현장 엔지니어가 매뉴얼을 짧은 시간 안에 훑고 설치 시작할 수 있어야 함"

### 2. 대상 사용자 (Who)
"누가 이 결과물을 보나?"

> 예: "고객사 현장 엔지니어 (한국어·영어 혼용 가능, 측정 장비 5년+ 경력)"

### 3. 성공 기준 (What)
"무엇을 만족하면 OK인가?"

> 예: "안전 규정 4가지 모두 포함 / Spec 표 5개 모두 포함 / 80% 이상 이미지 동봉"

### 4. 입력 자료
"어떤 자료를 참고할 것인가?"

> 예: "raw_data/NX-Interferom.txt + 형식/매뉴얼 형식_*.png"

### 5. 출력 형식
"결과물이 어떤 형태여야 하는가?"

> 예: "PDF · A4 · 회사 폰트 적용 · 페이지 번호 우측 하단"

### 6. 제약 사항
"하지 말아야 할 것"

> 예: "고객사명 직접 명시 X / 가격 정보 포함 X / 80자 이상 한 문장 금지"

### 7. 톤·스타일
"어떤 말투로?"

> 예: "격식 있는 영문 / 능동태 우선 / 기술 용어는 첫 등장 시 풀어쓰기"

### 8. 검증·재시도 규칙
"문제가 생기면 어떻게?"

> 예: "성공 기준 미달 시 자체 검토 후 보완 → 그래도 미달 시 '확인 필요' 보고"

## [실습] 본인 업무용 PRD 만들기

실제 본인 업무에 적용해보세요.

**Step 1.** 자주 하는 업무 1개 선택. (매뉴얼 작성, 진행 보고, 고객 응대 문구, 마케팅 카피 등)

**Step 2.** 클로드 코드에 입력:

```
[업무 이름] 작업을 위한 PRD를 만들고 싶어.
다음 8가지 섹션 채워줘:
1. 목적
2. 대상 사용자
3. 성공 기준
4. 입력 자료
5. 출력 형식
6. 제약 사항
7. 톤·스타일
8. 검증·재시도 규칙

각 섹션은 내가 답할 수 있는 질문 형태로 먼저 물어봐줘.
내 답을 들으면서 PRD 초안을 채워줘.
```

클로드가 질문을 하나씩 던지고, 여러분 답을 모아 PRD 한 장을 자동으로 만들어요.

**Step 3.** 완성된 PRD를 `.claude/agents/[업무이름].md` 로 저장.

→ 이제부터 그 에이전트를 호출할 때마다 PRD에 적힌 기준대로 일해요.

## [참고] PRD vs 에이전트 정의 차이

| 항목 | 에이전트 정의 (.claude/agents/) | PRD |
|---|---|---|
| 분량 | 짧음 (1~2 페이지) | 길음 (4~8 페이지) |
| 사용 시점 | 에이전트 만들 때 항상 | 복잡한 작업·중요 결과물 |
| 포함 정도 | 핵심 역할·규칙·금지 사항 | 위 8가지 섹션 모두 |
| 본 수업 예시 | PM.md, Editor.md | (본 수업엔 없음, 본업 적용 시 권장) |

쉽게 정리하면:

> 💡 **포인트**: 에이전트 정의 = 에이전트의 이력서 / PRD = 에이전트에게 주는 프로젝트 브리프.

## [Tip] 좋은 PRD 작성 3가지 팁

<SectionTitle icon="📌" title="1. 예시를 많이 넣기" sub="좋은 결과 + 나쁜 결과 둘 다" />

> ✅ "Park Systems의 사용자는 측정 정밀도 향상을 통해 분석 효율을 높일 수 있다." (능동태·짧음)
> ❌ "사용자에 의해 측정 정밀도가 향상됨으로써 분석 효율이 향상될 수 있을 것으로 여겨진다." (수동태·장황)

<SectionTitle icon="📌" title="2. 검증 가능한 기준으로" sub="추상적 표현은 OK인지 판단 불가" />

> "좋은 매뉴얼" → 너무 추상. "Spec 표 5개 모두 포함" → 검증 가능.

<SectionTitle icon="📌" title="3. 짧을수록 좋음" sub="길어지면 에이전트가 핵심을 놓침" />

> 8가지 섹션 모두 채우되, 각 섹션은 한두 문장으로. 길어지면 에이전트가 핵심을 놓침.
