# 11. 에이전트 & 하네스 엔지니어링 딥다이브

> 본 수업에서 짧게 소개한 **에이전트**와 **하네스** 개념을 좀 더 풀어드려요. 본업에 적용하실 때 두고두고 참고하실 자료입니다. 본 수업에서는 다루지 않은 내용이니 워크숍 후 본인 페이스로 읽어주세요.

---

## 본 수업 비유 다시 보기

| 단어 | 비유 |
|---|---|
| **에이전트 (Agent)** | 특정 역할이 정의된 AI 일꾼 — 정해진 입력·규칙·출력 양식으로 작업 수행 |
| **하네스 (Harness)** | 에이전트가 일 잘 하게 만드는 운영 시스템 — 어떤 파일을 읽고, 어떤 도구를 쓰고, 어떤 형식으로 결과를 내는지의 모든 약속 |

오늘 만든 두 에이전트 (PM 에이전트·에디터 에이전트)는 **에이전트**예요. 그 에이전트들이 사는 `.claude/agents/`, `.claude/commands/`, 작업 폴더 구조 모두가 **하네스**예요.

## [개념] AI가 일하는 방식의 시대 흐름

AI 도구는 시대별로 **달성하려는 목적**이 달라졌어요.

| 시대 | 도구 | 핵심 | 우리가 한 일 |
|---|---|---|---|
| **2023 — Prompt 시대** | ChatGPT, Claude 채팅, Gemini | "프롬프트를 잘 쓰면 좋은 답이 나옴" | 한 줄 잘 쓰기 |
| **2025 — Context 시대** | Cursor, Manus | "관련 자료(코드·문서·이미지)를 다 넘겨주면 더 좋은 답" | 자료 다 모아주기 |
| **2026 — Harness 시대** | Claude Code, Codex | "AI가 파일을 직접 만들고·고치고·테스트하는 작업 환경 자체를 잘 짜는 것" | **운영 시스템 만들기** |

> 오늘 우리가 한 게 바로 **3단계 Harness 시대**의 일이에요. 단순 프롬프트가 아니라, AI가 일할 수 있는 환경(폴더·커맨드·에이전트 정의) 자체를 만들었어요.

## [개념] 하네스가 풀어주는 두 가지 함정

같은 AI 모델인데 회사마다·사람마다 결과 품질이 다른 이유 — **하네스가 다음 두 가지 함정을 얼마나 잘 막아주는지**에 달려있어요.

<SectionTitle icon="⚠️" title="함정 1. 컨텍스트 불안 (Context Drift)" sub="대화가 길어지면 앞을 까먹음" />

> 대화가 길어질수록 AI가 앞의 작업·규칙·약속을 점점 잊어버려요. 결국 "대충 마무리"하려는 경향이 나타나죠.
>
> 예: 매뉴얼 작성 초반엔 회사 톤을 잘 지키다가, 후반엔 일반적인 영문 톤으로 흘러가버림.
>
> **하네스가 막는 방법**:
> - `CLAUDE.md` 같은 메모 파일에 핵심 규칙을 박아두기 (매번 다시 읽음)
> - 슬래시 커맨드로 작업을 작은 단위로 쪼개기 (한 번에 너무 길지 않게)
> - `/compact` 같은 명령으로 대화 압축

<SectionTitle icon="⚠️" title="함정 2. 자기 평가 편향 (Self-Evaluation Bias)" sub="본인 결과는 항상 좋다고 답함" />

> AI가 자기가 만든 결과를 객관적으로 비판하지 못해요. 본인이 만들면 대체로 "잘 됐다"고 평가하는 경향.
>
> 예: 에디터 에이전트에게 "방금 쓴 매뉴얼 어때?" 물으면 거의 항상 "좋다"고 답함.
>
> **하네스가 막는 방법**:
> - **만든 사람과 평가하는 사람을 분리** — 에디터 에이전트가 만들면, 평가 전담 에이전트가 따로 검수
> - 명확한 평가 기준 미리 정의 (체크리스트·규칙)
> - 사람이 최종 검수 단계에 반드시 개입

## [개념] 3-에이전트 패턴 — Planner / Generator / Evaluator

위 두 함정을 막는 가장 검증된 구조예요.

| 역할 | 하는 일 | 본 수업 비유 |
|---|---|---|
| **Planner** | 사용자 요청을 받아 구체적인 작업 명세로 변환 | "이 raw data를 어떤 형식으로 쓸지 정해줘" |
| **Generator** | 실제 콘텐츠 생성 | 에디터 에이전트가 변환 |
| **Evaluator** | 미리 정한 기준에 따라 검수·재작업 요청 | "회사 톤·기술 정확도·인용 형식 모두 충족했는지 점검" |

### 본 수업 패턴 vs 풀 3-에이전트 패턴

- **본 수업** = Generator 한 명만 (에디터 에이전트). 사용자가 직접 평가
- **본업 적용 시** = Planner + Generator + Evaluator 세 에이전트 분리하면 결과 품질·일관성이 크게 올라감

→ 본업 도입 시 "이 작업, 한 에이전트가 다 하기보다 세 명으로 나누면 어떨까?"를 먼저 생각해보세요.

## [개념] 하네스 엔지니어링이 뭐예요?

**하네스 엔지니어링** = AI 에이전트들이 **일관되게 좋은 결과를 내도록 운영 환경을 설계·관리하는 일**.

쉬운 비유:

> 회사에 새 AI 도구를 도입했다고 해봐요.
> - **AI 모델 성능**이 좋은 게 **일부**예요
> - **나머지**는 그 AI에게 어떤 입력을 주고, 어떤 도구를 쓰게 하고, 어떤 형식으로 결과를 내라고 정해두는 것 — 이게 **하네스**예요
>
> 같은 AI 모델이라도 **하네스가 잘 짜인 환경에서는 결과가 일관되고**, 하네스가 엉망인 환경에서는 매번 다른 결과가 나와요.

### 왜 필요한가요?

1. **예측 가능성** — 같은 명령에 비슷한 결과가 나와야 본업에 쓸 수 있음
2. **확장 가능성** — 새 에이전트를 쉽게 추가할 수 있어야 팀이 커져도 운영 가능
3. **회복 가능성** — 에이전트가 실수했을 때 사람이 개입할 수 있어야 함
4. **재사용 가능성** — 한 에이전트의 하네스 일부를 다른 에이전트에 재활용할 수 있어야 효율적

### 일반 소프트웨어 개발과 어떻게 다른가요?

| 일반 소프트웨어 | 하네스 엔지니어링 |
|---|---|
| 코드 자체가 결과를 결정 | **AI 에이전트의 운영 환경**이 결과 품질을 결정 |
| 같은 입력 → 항상 같은 출력 | 같은 입력 → 비슷한 출력 (확률적) |
| 디버깅 = 코드 수정 | 디버깅 = **에이전트 정의·규칙·환경 수정** |
| 한 번 만들면 끝 | 에이전트 결과 보면서 **계속 다듬어야 함** |

→ "코드를 잘 짜는 일"이 아니라 **"에이전트가 일할 회사를 설계하는 일"** 에 가까워요.

## [개념] 태스크별로 다른 하네스가 필요해요

에이전트 종류·작업 성격에 따라 하네스 설계가 다르게 가야 해요.

### 읽기 vs 쓰기

| 태스크 종류 | 하네스 강조점 |
|---|---|
| **읽기** (예: PM 에이전트 — 폴더 분석) | 폴더 구조 + 판정 규칙 + 보고 형식 |
| **쓰기** (예: 에디터 — 새 매뉴얼 생성) | 형식 학습 자료 + 톤 가이드 + 출력 위치 + 검증 기준 |

### 단일 작업 vs 반복 작업

| 태스크 종류 | 하네스 강조점 |
|---|---|
| **단일** (1회성) | 슬래시 커맨드 하나 + 명확한 입력·출력 |
| **반복** (매주·매일) | 에이전트 정의 + 슬래시 커맨드 + 결과 검증 단계 + 메모리(CLAUDE.md) |

### 본업 분야별

| 분야 | 하네스 우선순위 |
|---|---|
| **개발 (코드)** | 테스트·CI 연동 + 코드 리뷰 규칙 + 검증 루프 |
| **운영 (계약·세무)** | 보수적 모델 + 출처 모두 기록 + 사람 승인 단계 |
| **자료 제작 (PPT·매뉴얼)** | 톤·디자인 가이드 + 회사 톤 학습 자료 + 차례 비교 |
| **콘텐츠 (마케팅)** | 게시 채널 도구 + 톤 일관성 + 후보 여러 개 만들고 선택 |

→ 본인 본업이 어디에 가까운지 보고, 그에 맞춰 하네스 설계 우선순위를 정하면 효율적.

## [개념] 하네스를 만들 때 무엇이 중요한가

오늘 우리가 만든 하네스는 단순했어요. 회사 전체에 본격 도입할 땐 다음 4가지를 신경 쓰면 좋아요.

<SectionTitle icon="📌" title="1. 도구 관리 (Tools)" sub="에이전트가 쓸 수 있는 도구 범위" />

> 에이전트가 쓸 수 있는 도구(파일 접근·API 호출·외부 시스템 연결)를 미리 정해두기.
>
> 예: PM 에이전트는 `RFM/` 폴더만 읽기 / 에디터 에이전트는 `5_매뉴얼/` 폴더에서 읽고 쓰기 / arXiv API 호출 가능

<SectionTitle icon="📌" title="2. 액션 루프 (Action Loop)" sub="계획 → 실행 → 확인 사이클" />

> 에이전트가 한 번에 끝내지 못하는 일은 "계획 → 실행 → 확인 → 다음 행동" 사이클로.
>
> 예: 에디터 에이전트 = "raw data 읽기 → 형식 분석 → 변환 → 결과 확인 → 보완" 반복

<SectionTitle icon="📌" title="3. 상태 관리 및 평가 (State Management)" sub="어디까지 했는지·결과 품질 추적" />

> 에이전트가 어디까지 했는지, 결과 품질이 어떤지 추적.
>
> 예: PM 에이전트가 5단계 판정할 때 "이 폴더에 raw data 있음 → 1단계 → 다음 단계로 가려면 working/에 pdf 있어야 함" 식의 명확한 기준

<SectionTitle icon="📌" title="4. 메모리 관리 (Memory)" sub="매번 새로 시작하지 않도록 저장" />

> 에이전트가 매번 새로 시작하지 않도록, 사용자 선호·반복 결과·만족한 결과물을 저장하기.
>
> 예: `CLAUDE.md` 파일에 "우리 회사 제품명 표기 규칙", "본문 톤 가이드" 등을 적어두면 에이전트가 매번 참고

## [개념] 에이전트 사용 시 반드시 피해야 할 패턴 3가지

에이전트를 만들고 운영할 때 자주 빠지는 함정이에요. 본업에 적용 시 꼭 점검하세요.

<SectionTitle icon="🚫" title="1. 불확실한 fallback 금지" sub="모르면 추측하지 말고 '확인 불가'" />

> 에이전트가 모를 때 **추측해서 답하지 않게** 해야 해요. 잘못된 답이 자신감 있게 나오면 사람이 검증을 안 함 → 오류가 묻혀요.
>
> ✅ **좋은 예**: "RFM(M) 폴더에 자료가 없습니다. 확인 불가."
> ❌ **나쁜 예**: "RFM(M)은 아마 2단계인 것 같습니다." (근거 없는 추측)
>
> → 에이전트 정의에 "**모를 때는 추측 X, '확인 불가'로 답할 것**" 명시.

<SectionTitle icon="🚫" title="2. 검증 없는 종료 막기" sub="끝났다고 하기 전에 자체 점검" />

> 에이전트가 일을 끝냈다고 알릴 때, **결과가 진짜 맞는지 확인하는 단계**를 두기.
>
> ✅ **좋은 예**: 에디터 에이전트가 변환 완료 후 "원본의 핵심 정보 5개 중 5개 모두 포함됨" 자체 검증
> ❌ **나쁜 예**: 변환 완료 즉시 종료. 빠진 정보 있어도 모름
>
> → 슬래시 커맨드에 "**완료 전 자체 검증 단계 포함**" 명시.

<SectionTitle icon="🚫" title="3. 기능 경계 명확히 하기" sub="어디까지 에이전트, 어디부터 사람" />

> 이 에이전트가 **어디까지 할 수 있고, 어디부터는 사람이 결정해야 하는지** 미리 정해두기.
>
> ✅ **좋은 예**: "PM 에이전트는 진행 단계 판정·보고까지만. 일정 조정·우선순위 결정은 사람"
> ❌ **나쁜 예**: 에이전트가 알아서 일정도 바꾸고, 우선순위도 매김 → 사람이 의도 안 한 결과
>
> → 에이전트 정의에 "**이 에이전트가 하지 않는 일** 섹션" 명시 (오늘 PM 에이전트 만들 때 이미 한 패턴).

## [참고] 에이전트 vs 슬래시 커맨드

오늘 워크숍에서 두 가지를 모두 만들었는데, 정확히 뭐가 다른가요?

| 구분 | 에이전트 | 슬래시 커맨드 |
|---|---|---|
| **파일 위치** | `.claude/agents/` | `.claude/commands/` |
| **역할** | "어떤 에이전트인가"의 정체 (지속적) | "어떤 일을 하라"는 명령 (1회성) |
| **호출** | 다른 명령에서 자동 호출 또는 명시적 호출 | `/이름` 으로 사용자가 직접 |
| **오늘 만든 예** | `.claude/agents/PM.md`, `Editor.md` | `.claude/commands/progress.md`, `find-evidence.md` |

쉬운 비유:

> **에이전트 = 역할이 정의된 AI 일꾼** (정의 파일로 정체성·규칙 명시)
> **슬래시 커맨드 = 그 에이전트에게 시킬 일을 정해둔 메뉴판** ("/progress 시키면 이렇게 해" 약속)
