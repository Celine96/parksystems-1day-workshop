# 10. 에이전트 & 하네스 깊이

> 본 수업에서 짧게 소개한 **에이전트**와 **하네스** 개념을 좀 더 풀어드려요. 본업에 적용하실 때 두고두고 참고하실 자료입니다. 본 수업에서는 다루지 않은 내용이니 워크숍 후 본인 페이스로 읽어주세요.

## 본 수업 비유 다시 보기

| 단어 | 비유 |
|---|---|
| **에이전트 (Agent)** | 특정 일 잘 하는 전문 비서 |
| **하네스 (Harness)** | 비서가 일 잘 하게 만드는 회사 운영 시스템 (어떤 문서 어디 두고, 어떤 명령 받으면 뭘 하는지의 규칙) |

오늘 만든 두 비서 (PM 비서·매뉴얼 작가 비서)는 **에이전트**예요. 그 비서들이 사는 `.claude/agents/`, `.claude/commands/`, 작업 폴더 구조 모두가 **하네스**예요.

## [개념] AI가 일하는 방식의 시대 흐름

AI 도구는 시대별로 **달성하려는 목적**이 달라졌어요.

| 시대 | 도구 | 핵심 | 우리가 한 일 |
|---|---|---|---|
| **2023 — Prompt 시대** | ChatGPT, Claude 채팅, Gemini | "프롬프트를 잘 쓰면 좋은 답이 나옴" | 한 줄 잘 쓰기 |
| **2025 — Context 시대** | Cursor, Manus | "관련 자료(코드·문서·이미지)를 다 넘겨주면 더 좋은 답" | 자료 다 모아주기 |
| **2026 — Harness 시대** | Claude Code, Codex | "AI가 파일을 직접 만들고·고치고·테스트하는 작업 환경 자체를 잘 짜는 것" | **운영 시스템 만들기** |

> 오늘 우리가 한 게 바로 **3단계 Harness 시대**의 일이에요. 단순 프롬프트가 아니라, AI가 일할 수 있는 환경(폴더·커맨드·비서 소개서) 자체를 만들었어요.

## [개념] 하네스를 만들 때 무엇이 중요한가

오늘 우리가 만든 하네스는 단순했어요. 회사 전체에 본격 도입할 땐 다음 4가지를 신경 쓰면 좋아요.

### 1. 도구 관리 (Tools)

비서가 쓸 수 있는 도구(파일 접근·API 호출·외부 시스템 연결)를 미리 정해두기.

> 예: PM 비서는 `RFM/` 폴더만 읽기 / 매뉴얼 작가 비서는 `3교시_매뉴얼/` 폴더에서 읽고 쓰기 / Semantic Scholar API 호출 가능

### 2. 액션 루프 (Action Loop)

비서가 한 번에 끝내지 못하는 일은 "계획 → 실행 → 확인 → 다음 행동" 사이클로.

> 예: 매뉴얼 작가 비서 = "raw data 읽기 → 형식 분석 → 변환 → 결과 확인 → 보완" 반복

### 3. 상태 관리 및 평가 (State Management)

비서가 어디까지 했는지, 결과 품질이 어떤지 추적.

> 예: PM 비서가 5단계 판정할 때 "이 폴더에 raw data 있음 → 1단계 → 다음 단계로 가려면 working/에 pdf 있어야 함" 식의 명확한 기준

### 4. 메모리 관리 (Memory)

비서가 매번 새로 시작하지 않도록, 사용자 선호·반복 결과·만족한 결과물을 저장하기.

> 예: `CLAUDE.md` 파일에 "우리 회사 제품명 표기 규칙", "본문 톤 가이드" 등을 적어두면 비서가 매번 참고

## [개념] 에이전트 사용 시 반드시 피해야 할 패턴 3가지

비서를 만들고 운영할 때 자주 빠지는 함정이에요. 본업에 적용 시 꼭 점검하세요.

### 1. 불확실한 fallback 금지

비서가 모를 때 **추측해서 답하지 않게** 해야 해요. 잘못된 답이 자신감 있게 나오면 사람이 검증을 안 함 → 오류가 묻혀요.

> ✅ **좋은 예**: "RFM(M) 폴더에 자료가 없습니다. 확인 불가."
> ❌ **나쁜 예**: "RFM(M)은 아마 2단계인 것 같습니다." (근거 없는 추측)

→ 비서 소개서에 "**모를 때는 추측 X, '확인 불가'로 답할 것**" 명시.

### 2. 검증 없는 종료 막기

비서가 일을 끝냈다고 알릴 때, **결과가 진짜 맞는지 확인하는 단계**를 두기.

> ✅ **좋은 예**: 매뉴얼 작가 비서가 변환 완료 후 "원본의 핵심 정보 5개 중 5개 모두 포함됨" 자체 검증
> ❌ **나쁜 예**: 변환 완료 즉시 종료. 빠진 정보 있어도 모름

→ 슬래시 커맨드에 "**완료 전 자체 검증 단계 포함**" 명시.

### 3. 기능 경계 명확히 하기

이 비서가 **어디까지 할 수 있고, 어디부터는 사람이 결정해야 하는지** 미리 정해두기.

> ✅ **좋은 예**: "PM 비서는 진행 단계 판정·보고까지만. 일정 조정·우선순위 결정은 사람"
> ❌ **나쁜 예**: 비서가 알아서 일정도 바꾸고, 우선순위도 매김 → 사람이 의도 안 한 결과

→ 비서 소개서에 "**이 비서가 하지 않는 일** 섹션" 명시 (오늘 PM 비서 만들 때 이미 한 패턴).

## [참고] 에이전트 vs 슬래시 커맨드

오늘 워크숍에서 두 가지를 모두 만들었는데, 정확히 뭐가 다른가요?

| 구분 | 에이전트 | 슬래시 커맨드 |
|---|---|---|
| **파일 위치** | `.claude/agents/` | `.claude/commands/` |
| **역할** | "어떤 비서인가"의 정체 (지속적) | "어떤 일을 하라"는 명령 (1회성) |
| **호출** | 다른 명령에서 자동 호출 또는 명시적 호출 | `/이름` 으로 사용자가 직접 |
| **오늘 만든 예** | `.claude/agents/PM.md`, `Manual-Writer.md` | `.claude/commands/progress.md`, `find-evidence.md` |

쉬운 비유:

> **에이전트 = 부서에 새로 들어온 비서 한 명** (이력서·소개서를 갖고 있음)
> **슬래시 커맨드 = 그 비서에게 시킬 일을 정해둔 메뉴판** ("/progress 시키면 이렇게 해" 약속)
